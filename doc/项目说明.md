
# 草稿 

**目的** 实现双端 多渠道/站点监控

**监控端**(底层框架依赖)
- 本机监控 Uptime Kuma
- 国际边缘终端 cloudflare tunner

**场景**
- 渠道测试监控 自己启动一个小服务 通过不同渠道进来监控
  - 渠道可选列表 [clowdflare-tunnel,pst(阿里ecs),华为云 DevBridge,SakuraFrp,OpenFrp, ChmlFrp,花生壳,NATAPP]
- 业务监控 [xxx..trycloudflare.com,pst,/*其他自定义站点*/]


**说明**
- 站点: 一个目的服务器+测试方法(如一个测试接口路径+返回值判断)，一个站点/站点功能对应一个测试方法
- 渠道: 通过不同渠道访问同一个服务 就是同样的测试方法换了不同的域名/baseurl
- 渠道配置: = 测试方法 + 渠道


**要求**
集中 扁平化的配置文件 按监控端归为2个配置:
- 本机监控
  - 监控端配置+n(渠道配置<-渠道/站点)
- 国际边缘监控
  - 监控端配置+n(渠道配置<-渠道/站点)

**项目结构/目录**
- 本机监控框架
- 国际边缘终端监控框架[UptimeFlare-Cloud-DSH 仓库 可能需要耦合层]
- 通用方法
  - 渠道信息
  - utils
  - 如站点检测([{site,baseurl,testmeth,公共的东西}])
  - 其他
- 渠道测试监控场景
  - 本机监控 监控端配置+n(渠道配置<-渠道/小测试服务)
  - 国际边缘监控 监控端配置+n(渠道配置<-渠道/小测试服务)
- 业务监控场景
  - 本机监控 监控端配置+n(渠道配置<-渠道/站点)
  - 国际边缘监控 监控端配置+n(渠道配置<-渠道/站点)

渠道配置可以 [(import站点 + 渠道)*n, 其他自定义]

**命令结构**
- cmd: 启动场景 -渠道测试监控场景目录
  - cmd: 启动本机监控 -渠道测试/本机监控目录
  - cmd: 国际边缘监控 -渠道测试/国际监控目录
- cmd: 启动场景 -业务监控场景目录
  - cmd: 启动本机监控 -业务监控/本机监控目录
  - cmd: 国际边缘监控 -业务监控/国际监控目录

每个命令都可以单独执行

**关联**
你可能需要考虑如何对接到UptimeFlare-Cloud-DSH项目,多个监听同时跑代码什么框架 (你可以在项目同级目录找到)

# 项目设计

## 已定

本仓库管监控的全流程下发，不把渠道拉起来。tunnel / frp / 花生壳等由用户按 demo 自己起。探测仍用现成两端：本机 Uptime Kuma；国际边缘用同级已改过的 UptimeFlare-Cloud-DSH，不从上游 UptimeFlare 重新 fork。

边缘是耦合层加部署脚本。新环境从模板拉出，配置写进对应仓库再发布。本地只留一个 UptimeFlare 工作副本，用多分支对多个远端：每个环境一条分支，上游绑到该远端的 `main`（`git push -u <远端> <分支>:main`）。之后切到该分支再 push，就会更新那个仓库的 `main`，由该仓库的 GitHub Action 部署。模板单独一条 `template` 分支，不拿正在跑的 `main` 当模板。已有业务环境不改名：本地分支 `Cloud-DSH` 绑定远端 `UptimeFlare-Cloud-DSH` 的 `main`。新场景默认：分支名等于场景目录名，远端仓库名等于 `UptimeFlare-` 加场景目录名，再绑到该远端的 `main`。国际配置里写了仓库时以配置为准，建仓库和绑定都用这个名字，不再按场景名推导。

远端仓库可以由命令自动建。本机已登录 `gh`，且环境变量里有 `CLOUDFLARE_API_TOKEN` 时：建不带 README 的空仓库、写入 Secret、再把本地分支 push 到该远端 `main`。没有 Token 就停，不建仓库。步骤见 `doc/UptimeFlare-部署.md`。部署失败时先看官方 [Quickstart](https://github.com/lyc8503/UptimeFlare/wiki/Quickstart)；官方没写的权限清单也在该文档。

同一个 Cloudflare 账号。已有业务环境继续用现名 `uptimeflare_d1`、`uptimeflare_worker`、`uptimeflare`。新场景发布前按场景名改这三项，各用各的资源，避免后发布的盖掉先发布的。

场景目录放在仓库根上，可以继续加，不收进统一的 `scenarios/`。目录名统一带后缀 `-sc`，例如 `channel-test-sc`、`cloud-dsh-sc`。通用层是根上的 `shared/`。每个场景固定两个子目录：`local`、`intl`（国际，不用 edge）。启动场景只认这两个名字。每个叶子只认一个入口 `config.mjs`，复杂逻辑 import。它导出一个对象，里面是 endpoint 和 monitors。本机 endpoint 含端口、状态页、默认间隔；国际 endpoint 含远端、分支、页面标题。monitors 是引用项和自定义项的数组。通用的站点、渠道、检测放 `shared/`。不通用的不规定路径和文件名，写在哪由使用的人自己 import。渠道项是 `(引用站点 + 渠道) × n`，再加自定义项。

场景名用来做 Docker 名和 UptimeFlare 分支名。路径上能找到 `*-sc` 目录时用该目录名；找不到时，配置对象里必须写场景名。

字段：站点带检测（路径、方法；关键字和期望状态码可选）。渠道只有 baseurl。地址 = baseurl + 路径。自定义项自己写完整地址和检测。关键字、状态码都空时仍然有效，只判断请求成功（默认 2xx，不看正文）。本机入口另有端口和状态页；国际入口另有远端和分支。通用项和场景项同一套字段。

每个场景各一套运行，不共用一个 Kuma 或一个边缘环境。叶子目录的配置就是 `config.mjs`，不另写状态文件。Kuma 数据在该 `local/data/`。`monitors.json` 是下发结果，不手改。边缘仓库不嵌进场景目录。

是创建还是更新，看现场：本机看该场景的 Docker 和 `data/` 在不在；国际看绑定的分支和远端在不在。在就更新，不在就创建。

没有单独的 demo 目录，渠道测试场景目录本身就是 demo。渠道清单在通用层的渠道模块里：做和不做的都列在那里，不做的只留注释。第一版做这五个：cloudflare-tunnel、pst（阿里 ECS）、华为云 DevBridge、SakuraFrp、花生壳。OpenFrp、ChmlFrp、NATAPP 以及其他不做的，在通用层和渠道测试场景里都用注释留着，不实现。

三条命令的参数都是实际目录：

- 启动本机 — 某个 `local` 目录
- 启动国际 — 某个 `intl` 目录
- 启动场景 — 某个场景目录（里面用 `local` 和 `intl`）

第一次跑创建，之后跑更新。现有 flashcat 脚本和包名拿掉。本机框架留下：`kuma.mjs`、compose、status-v2，同一套代码按目录起独立实例。
